## 작업 기본 원칙
- 세션 시작 시 프로젝트 루트의 `readme.md`를 먼저 확인하고 작업한다.
- 임기응변식 패치가 아니라 근본 원인 기준으로 수정한다.
- Vercel 배포 기준에서 오류 없이 동작하도록 작성한다.

## 작업 프로세스 (Workflow)
- 선(先) 분석 보고: 요청 시 즉시 코드 수정하지 않고 반드시 `[분석 리포트]`를 먼저 제시한다.
- 분석 포맷: `1. 현재 로직/문제점 -> 2. 수정 방향/기술 -> 3. 적용 계획(대상 파일)`.
- 후(後) 실행: 사용자의 명시적 실행 명령(예: `ㄱㄱㄱ`) 이후에만 파일 수정(write/replace) 수행.
- 디자인 수정: UI/색상 변경 시 2가지 시안을 먼저 제안한다.

## UI/라우트 변경 규칙 (유기적 처리 필수)
- 버튼/메뉴/UI 컴포넌트/라우트 추가·삭제·변경 시 해당 파일만 수정하지 말고 연쇄 영향까지 함께 처리한다.
- 점검 범위: 네비게이션(사이드바/헤더), 링크 경로, 권한 분기, 상태 로딩/에러 처리, API 호출, 타입, 빈 화면/스켈레톤, 테스트/빌드 영향.
- 처리 원칙: 원인 지점과 연결 지점을 한 번에 수정해 사용자 플로우가 끊기지 않게 마무리한다.
- 금지 사항: 증상만 막는 임시 패치, 동일 로직 중복 추가, 하드코딩 확장.
- 완료 기준: 변경된 UI/라우트에서 실제 진입/이동/액션 흐름이 끝까지 정상 동작해야 완료로 본다.

## 공통 UI 컴포넌트 관리 원칙
- 아이콘/뱃지/카드/버튼처럼 다방면에서 반복 사용되는 요소는 반드시 공통 컴포넌트로 관리한다.
- 동일한 역할의 UI가 여러 곳에서 필요할 때는 화면별 복붙 구현을 금지하고, 공통 컴포넌트(또는 공통 훅/유틸)로 먼저 추상화한 뒤 사용한다.
- 캠페인 카드/플랫폼 뱃지처럼 데이터 해석 규칙이 포함된 UI는 단일 기준 로직을 공유하여, 메인/목록/상세/즐겨찾기 등 모든 화면에서 같은 결과가 나오게 한다.
- 디자인 변경 시에도 공통 컴포넌트 기준으로 일괄 반영되게 구성해 화면 간 이질감을 방지한다.
- 목표: 한 곳만 수정해도 전체 화면에 동일한 디자인과 데이터 규칙이 적용되도록 유지한다.

## UI/UX 가이드
- 스켈레톤 로더: 데이터 로딩 중 빈 화면 금지. 레이아웃 뼈대를 먼저 노출해 체감 속도를 높인다.

## 터미널/실행 제약
- 설치/복사 등 30초 이상 소요 작업은 직접 실행하지 않고, 사용자 실행용 명령어를 `bash` 코드블록으로 제공한다.

## 운영 문서
- 맥미니 영상 워커 운영은 `docs/video-worker-macmini-runbook.md`를 기준으로 진행한다.

## 난이도 높은 작업 대응
- 진행이 막히면 코드를 무작정 바꾸며 반복 시도하지 않는다.
- 현재 상황/막힌 원인/다음 방향을 먼저 보고하고, 합의된 방향으로 재이행한다.
