# 다온뷰 작업일지 — 2026-11-22

## 오늘의 요약

사이트 전반의 인증·데이터 조회 성능 개선을 코드에 반영했다. 기존 스켈레톤을 유지하면서 인증과 초기 데이터의 중복 조회를 줄이고, 공개 캠페인 캐시와 변경 후 무효화 경로를 정리했다.

격리 회귀 테스트 53개, TypeScript 검사, 프로덕션 빌드는 통과했다. 실제 로그인 상태의 전후 성능 비교는 미완료이며, DB에서 발견한 기존 RLS 문제는 배포 전 해결해야 한다. 이번 구현은 운영에 배포하지 않았다.

## 1. 공통 인증·권한 개선

- 서버 인증과 프로필 조회를 요청 단위 React `cache()`로 공유하도록 구성했다.
- `requireDashboardRole()`의 기존 반환 계약과 관리자 별칭 ADMIN/MASTER/SUPER_ADMIN을 유지했다.
- 역할은 DB `profiles.role`로 판정하고, `user_metadata.role` 대체 경로를 제거했다.
- 관리자·광고주·인플루언서 페이지와 공통 캠페인 페이지에 서버 역할 검사를 연결했다.
- 미들웨어의 역할 DB 조회를 제거하고 세션 갱신·쿠키 전달·비로그인 차단을 유지했다. 인증 서버 통신 실패는 503으로 구분했다.
- 클라이언트는 유효한 SSR 프로필을 초기 인증 이벤트에서 재사용하고, 동일 사용자의 동시 프로필 요청을 합치도록 했다.
- 프로필 조회 오류를 별도 상태로 표시하고, 로그아웃·계정 전환·화면 이탈 뒤 도착한 응답을 무시하도록 보완했다.

미들웨어와 서버 렌더링의 `getUser()`는 실행 경계가 달라 각각 유지된다. 모든 인증 통신이 한 번으로 줄었다는 의미는 아니다.

## 2. 공개 데이터 캐시·갱신 개선

| 대상 | 처리 |
|---|---|
| 홈 배너 | 기존 60초 캐시 유지, 독립 조회 병렬화 |
| 공개 캠페인 목록·관련 캠페인 | 30초 캐시 |
| 캠페인 상세·메타데이터 | 캠페인별 60초 캐시, 원본 조회 공유 |
| 공개 리뷰 | 기존 주간 스냅샷 정책 유지 |
| 커뮤니티 상세 | 메타데이터·본문의 중복 원본 조회를 요청 안에서 공유 |
| 개인 신청·배정 구매 링크·정산 정보 | 공용 캐시 제외 |

- 캐시 저장 전에 공개 DTO를 만들고 결제·쿠폰·임시저장 정보와 비공개 구매 링크 풀을 제거했다.
- 비공개 캠페인 미리보기는 소유자·관리자 권한 확인 후 공용 캐시 밖에서 조회하도록 했다.
- 공통 무효화 함수를 등록·수정·임시저장·삭제·승인·마감·재개·연장·자동 연장·구매 링크 변경·신청·취소·선정·재할당·리뷰 제출 경로에 연결했다.
- 관련 브라우저 직접 쓰기를 서버 API로 옮기고 역할·소유권·입력 검사를 연결했다.
- 신청 가능 여부와 선정 인원은 최신 DB로 확인한다. 본인 작업 성공 후 화면 데이터와 집계를 갱신하도록 했다.
- 저장 성공 뒤 캐시 무효화만 실패하면 별도 경고를 반환한다. 쓰기 작업을 자동 재시도하지 않는다.

## 3. 역할별 화면 개선

- 인플루언서 요약·참여 캠페인·찜·리뷰와 광고주 요약·캠페인·리뷰에 서버 초기 데이터를 전달했다.
- 최초 렌더 직후 같은 데이터를 다시 조회하는 경로를 줄이고, 필터 변경과 작업 후 조회는 유지했다.
- 관리자 캠페인 목록과 사이드바 집계 등 독립 조회를 병렬화했다.
- SSR 집계가 있는 사이드바는 마운트 직후 중복 조회를 생략한다. 숨겨진 탭에서는 조회를 중단하고, 작업 후 갱신 요청이 겹치지 않도록 했다.
- 내 문의의 인증 조회를 공통 인증 함수로 연결했다.
- 캠페인 운영은 기존 `CampaignDataTable`과 역할별 래퍼 구조를 유지했다.
- 온보딩·프로필 오류 처리와 계정 전환 중 알림 생성의 응답 경합을 보완했다.

## 4. 카카오 안내 관련 논의

대화에서 정리한 방향이며, 실제 웹 연동·발송 완료로 기록하지 않는다.

- 기본 선정 시 자동 카카오 발송을 끄고, 보류 대상은 운영자가 수동 버튼으로 발송하는 흐름을 요청했다.
- 특정 브랜드 전용이 아닌 범용 강조표기형 가이드 템플릿을 검토했다.
- 본문 변수는 인플루언서명·캠페인명·제공내역·진행가이드·주의사항으로 구성하고, 캠페인 확인 버튼에는 캠페인ID 변수를 사용하는 방향을 정리했다.
- 대체 문자는 선정 안내, 진행가이드, 주의사항, 캠페인 가이드 링크로 구성했다.
- 사용자가 템플릿 검수 결과를 알려주기로 했다. 검수 완료와 실제 테스트 수신·변수 치환 완료는 확인되지 않았다.

## 6. 발견한 문제와 다음 작업

### 배포 전 우선 해결: 기존 RLS 정책

DB 정책과 권한을 읽기 전용으로 확인한 결과:

- `profiles`의 `Allow All Profiles`, `campaigns`의 `Allow All Campaigns`가 `ALL USING true WITH CHECK true` 형태다.
- 두 테이블에 anon 역할의 SELECT/INSERT/UPDATE/DELETE 권한이 있다.
- 신청 공개 읽기 정책과 개별 배정 링크 등 민감 컬럼의 직접 접근 범위도 추가 점검이 필요하다.

서버 검사만으로 직접 Data API 접근을 막을 수 없으므로, 사이트 전체 권한 안전성은 통과 처리하지 않았다. DB 정책 변경은 이번 범위에서 제외되어 실행하지 않았다.

### 남은 검증

1. 격리 환경의 세 역할 계정으로 실제 JWT/RLS 교차 접근과 소유권 차단을 확인한다.
2. 만료·갱신 세션, 로그아웃·계정 전환, 프로필 수정 후 재표시를 실제 로그인 상태에서 확인한다.
3. 저장·신청·선정·취소·연장 후 홈·목록·상세·건수 갱신을 확인한다.
4. 동일 환경·계정에서 각 5회 성능을 비교한다. 본문 표시 중앙값이 10% 이상 악화되면 원인을 해결하거나 해당 단계를 되돌린다.
5. RLS 보완과 미완료 검증을 마친 뒤 별도 배포 요청에 따라 운영 반영한다.

### 기존 중복 정의

`constants/role.ts`와 `campaignPermissions.ts`에 역할 정규화·관리자 별칭 정의가 중복돼 있다. 현재 호출부가 없는 예전 `CampaignTableClient.tsx`도 확인했다. 별도 통합 여부를 검토할 대상으로 남겼다.

## 7. 변경하지 않은 범위

운영 배포·커밋·푸시, DB 데이터·정책·스키마, 환경변수·인증키, 새 의존성은 변경하지 않았다. 실제 메시지 발송이나 결제 테스트도 수행하지 않았다.
