- 알림 조회 개수 제한·컬럼 선택은 미적용: 테이블 컬럼 8개뿐이고 사용자당 최대 33건이라 미읽음 수 왜곡 위험만 있음.

## 6-3. Gemini AI 기능 전체 장애 수정

- 원인: `gemini-2.0-flash` 지원 종료(404). 공용 `generateWithGemini`를 쓰는 기능 전체(칼럼 크론, 사업자 인증 확인, 키워드 추천, 커뮤니티 AI 피드백, AI 글쓰기, 키워드 분석, 랜딩 생성) 실패. 다온 지수의 `gemini-2.5-flash`도 신규 사용자 차단 대상.
- 조사: AI Studio에서 키는 이미 "Gemini API" 제한이 걸려 있고 모두 무료 등급 확인(키 설정 변경 없음). 공식 문서상 2.5 계열은 기존 사용자만 접근 가능, 2026-12-01부터 `gemini-2.5-flash`는 `gemini-3.5-flash-lite`로 자동 전환. 3.x 모델은 `v1`에선 404, `v1beta` generateContent에선 정상.
- 수정: 공용 `GEMINI_TEXT_MODEL`(기본 `gemini-3.5-flash-lite`, `GEMINI_MODEL` 환경변수로 교체 가능)·`GEMINI_GENERATE_URL`(v1beta)·`extractGeminiText`(텍스트 조각 합치기) 추가, `googleAI.ts`·`generate-landing`·`daon-index` 적용.
- 검증: 실제 코드 경로 호출로 JSON·텍스트 응답 정상, tsc 통과, ESLint 신규 0건, 테스트 75개 통과. 칼럼 크론은 실제 발행되므로 수동 실행하지 않고 다음 정기 실행(격일 01:00 UTC)에서 확인 필요.
- 참고: API 키가 URL 쿼리(`?key=`)로 전달됨 — 헤더(`x-goog-api-key`) 전환 검토. "서버 키 1"(2016, 제한 없음)은 다른 용도 가능성이 있어 변경하지 않음.

## 6-4. RLS 이후 신청 수 집계 오류 수정

- 원인: 11-22 RLS 강화 후 비관리자 세션의 `applications(count)`는 본인 신청만 센다.
- 영향: ① 신청 API(`/api/applications/mutate`)의 모집 마감 판정이 선정 인원을 0/1로 계산 → **마감된 캠페인에도 신청 가능**했던 상태, ② 추천 페이지가 마감 캠페인을 신청 가능으로 표시, ③ 찜 카드(상단 메뉴·찜 페이지) 신청자 수 축소 표시.
- 수정: 5곳을 DB 계산 컬럼 `applicant_count, selected_count` 조회 + 기존 `withRelationCounts` 변환으로 교체(`mutate/route.ts`, `recommended/page.tsx`, `cartStore.ts`, `favorites/PageClient.tsx`, `dashboardData.ts`). 회귀 테스트를 계산 컬럼 기준으로 갱신.
- 검증: 테스트 75개 통과(마감 캠페인 신청 차단 포함), tsc 통과, ESLint 신규 0건, 빌드 통과, 공개 REST로 캠페인 44 계산 컬럼 33/24 확인. 인플루언서 로그인 화면 확인은 미수행.
- 이후 추가 수정: 신청 직후 모집률 알림(50/100/120%) 계산도 사용자 세션 count라 본인 신청만 셌음 → `applicant_count` 재조회로 수정(남은 이슈 11번).

## 6-5. 공개 캠페인 캐시 재검증 실패 보완 (`c50ce7f` 배포됨)

- 현상: 최근 7일 4건(캠페인 44·1·34·13), 마지막 11-24 19:06 KST. 일지의 "05:41 KST"는 이후 발생분으로 대체.
- 원인 확인: 19:06:38 캠페인 34 실패 시각에 Supabase edge 로그에 해당 조회 요청 자체가 없음(같은 시간대 다른 캠페인 조회는 200). 직전 PostgREST `Thread killed by timeout manager`, 11-22 `fetch failed / other side closed` 기록. → RLS·데이터 문제가 아니라 **유휴 상태에서 끊긴 연결 재사용으로 요청이 Supabase에 도달하지 못한 네트워크 실패**로 판단(재현은 안 함).
- 수정: `src/lib/publicCampaignServer.ts` 공개 목록·상세 조회에 `runPublicRead` 추가 — 오류 코드가 빈 네트워크 실패만 1회 재시도(읽기 전용), DB 오류(`42501` 등)는 즉시 실패. 실패 시 원래 오류 코드·메시지를 로그에 남김.
- 검증: ESLint(대상 파일) 통과, tsc 통과, 회귀 테스트 76개 통과, 모의 클라이언트로 재시도 동작 확인(네트워크 실패→재시도 후 성공, 권한 오류→재시도 없음, 2회 실패→오류, 정상→1회 조회). 운영 배포 후 주요 화면 200·오류 로그 0건 확인. 실제 연결 끊김 상황의 재시도 효과는 아직 미확인.
- 변경하지 않음: 캐시 시간(30·60초), 캐시 무효화, DB·RLS, 다른 공개 조회(배너·공지 등 — 같은 연결 문제 가능성 있음, 필요 시 별도 검토).

## 6-6. 선정 메일 반송자 카카오 알림톡 수동 발송

- 배경: 솔라피 템플릿 "인플루언서 체험 진행 가이드" 승인. 선정 메일이 반송된 보류 건에 관리자가 버튼으로 알림톡을 보내는 흐름.
- 기존 문제(수정 전 점검):
  - `/api/send-alimtalk`이 인증 없는 공개 API → 선정 템플릿은 거부하도록 차단(나머지는 기존 `ALIMTALK_PAUSED`로 계속 중지).
  - 코드 변수(체험유형·마감일 등)가 승인 템플릿 변수와 불일치, `진행가이드`·`주의사항` 누락.
  - 환경변수 템플릿 ID가 승인 ID와 달랐음.
  - 일시정지 해제 시 선정자 전원 자동 발송 구조였음 → 자동 발송 분기 제거.
- 구현:
  - 관리자 전용 `POST /api/applications/[id]/selection-kakao`, `src/lib/selectionKakaoServer.ts`. 활성 보류·선정 상태·번호 확인 후 발송 기록(`PREPARED`)을 먼저 남기고 발송. 문자 대체 발송 끔(`disableSms`).
  - 결과 상태: 접수 거부 `FAILED`(재발송 허용), 네트워크 등 불확실 `UNKNOWN`(재발송 차단, 솔라피 내역 확인 필요).
  - 메일과 같은 정보: `src/lib/selectionContent.ts` 공통 함수로 메일·카톡이 같은 값 사용(제공내역·확정옵션·구매링크·핵심 가이드·주의사항·체험 마감기한). 개별 링크 캠페인인데 배정 링크 없으면 발송 거부. 구매링크는 자르지 않고 1,000자 이내로 가이드·주의사항을 줄임.
  - 관리자 신청자 표(시안 A): 보류 칸에 `카톡 발송`/`보류 해제` 버튼, 발송 상태·시각 표시, 확인 창에 마스킹된 번호. 발송 성공 후 보류 해제 시 사유 자동 입력.
- 검증: tsc 통과, 수정 파일 ESLint 신규 오류 0건(기존 3건 유지), 카톡 테스트 7개 + 기존 29개 통과, 프로덕션 빌드 통과.
- 실제 발송 테스트(테스트 계정 1건씩, DB 기록 없이 같은 변수 생성 코드로 직접 발송):
  - 캠페인 20: 수신 완료(4000). 이 캠페인은 가이드·주의사항이 비어 있어 대체 문구 표시.
  - 캠페인 44(이큐비아): 417자, 구매링크·확정옵션·마감기한 포함, 수신 완료(4000), 문자 대체 없음.
- 미검증: 관리자 화면 버튼 → API → 발송 기록 저장 실제 경로(가짜 DB 테스트만). 테스트 계정에 활성 보류 건이 없어 실제 보류 건 발생 시 첫 사용.
